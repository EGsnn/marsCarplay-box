# 0.1.2：80 MHz PSRAM 与板端性能测量

日期：2026-10-26。固件 `0.1.2-atk-psram80`。

## 目标与基线

0.1.1 已经通过真实手机直显及无数据页闪切验收。用户随后目测反馈约 2–4 秒一帧（约 0.25–0.5 FPS），尚无 0.1.1 的定量性能采集。本版先单独提高 PSRAM 速度并测量，不把主机解码结果当作 S3 性能，也不预先承诺帧率提升。

## 修改

- PSRAM 从原构建默认 40 MHz 改为 80 MHz；CPU 保持 240 MHz，8 MiB Octal PSRAM 与启动内存测试继续启用。
- `build.py --fresh-config` 在保存原构建配置后，从本项目默认值重新生成配置，避免旧 sdkconfig 缓存继续选择 40 MHz。普通构建保留当前配置。
- 独立于 HTTP 请求，由主任务每约 250 ms 采样计数，以至少一秒的实际时间窗口计算接收、解码、成功 LCD 提交帧率。空闲后帧率归零，不用“上一帧耗时倒数”冒充连续显示 FPS。
- 解码帧在解码回调时计数，与实际 LCD 成功提交计数分开；旧配置结果即使被拒绝绘制，仍反映发生过解码。
- 累计解码尝试、颜色转换/LCD 提交尝试的平均和最大耗时；解码耗时扣除完整显示回调，包含解析、调度和协作等待，属于墙钟时间，不是纯 CPU 时间或端到端延迟。
- 状态接口增加编译配置的 PSRAM/CPU MHz、队列状态、解码器重建次数与等待关键帧时跳过的帧数。队列 evicted 统计的是环形队列淘汰，包含已读帧；不能直接当作显示端丢帧，实际缺口看 gaps。
- 保持现有 800×480 / maxFPS 30 能力声明、H.264 解码内核、关键帧恢复策略、LCD 与触摸路径；诊断页保持隐藏，避免把多项优化混在一次对比中。
- 增加可选的 `code/tools/collect_performance.command` / `.py`，仅采集 JSON 数值并保存至忽略的 build/performance/，不作为视频中继。

## 检查与产物

- S3 构建通过；最终 ELF 实际包含 80 / 240 MHz 配置，USB iAP2/NCM 与 BOARD 320×240 / 16 MiB / 8 MiB 检查通过，旧诊断绘屏入口未链接。
- ASan/UBSan 下的统计检查通过：独立帧率、不等长采样窗口、空闲归零、计数绕回、无样本与平均/最大耗时单位；这些合成检查值不代表板端 FPS。
- 实际生产解码与 RGB 路径再次处理真实 124 帧通过；原上游三处 uint8 与 256 比较警告仍保留。
- 采集脚本已检查独立 FPS 汇总、拒绝计数回退/重启区间以及空采集不生成虚假帧率。
- 后续新增模拟发送端，并以主机原生接收代码完成 Pair-Setup / Pair-Verify / 加密控制及视频验证：300 帧接收、解码、RGB 转换成功，0 错误。没有修改本版固件；这不是 S3 性能结果，边界见 references/simulation-test-2026-10-26.md。
- 候选 1,213,616 B，SHA-256 `6dd72c694a147ec367cdb39a1ecb812a2e0f300b6e9d8b44021418b132c03ac3`。

## 安装与实物状态

已识别同一 BOX：MAC `[device MAC omitted]`、16 MiB Flash / 8 MiB PSRAM。更新前用 ROM 摘要确认当前全 16 MiB 与已保存的 0.1.1 镜像一致，另存本版全量回退镜像与原应用槽；分区表与 OTA 校验确认当前选择 `ota_0 @ 0x10000`。

已仅写入应用，独立读回与候选逐字节一致。全 Flash 摘要与仅替换应用擦除范围的期望镜像一致，其他分区受保护。最初仍在下载模式；用户释放 BOOT 并实体复位后，USB/NCM 正常枚举。状态接口确认本版运行、显示任务就绪、PSRAM 80 / CPU 240 MHz 编译配置及 RTSP 监听。启动状态和安装清单已更新保存在本地备份目录。

随后已向物理 BOX 模拟发送真实样本：高负载 30 秒实际发送/收到 662 帧，另等 3 秒后仅解码/提交 15 帧，新增 15 次序列缺口；低负载 1 FPS 发送 20 帧，20 帧全部解码/提交，零缺口、零错误。高/低负载解码墙钟均值分别约 1309 / 518 ms，转换约 50 / 23 ms，LCD 提交约 17 / 16 ms。高负载反复等待并请求 IDR，主要瓶颈是慢解码和随后的队列缺口恢复。高负载实际发送为 22.07 FPS，未达到目标 30 FPS；没有旧 40 MHz 版本的相同测试，不能量化本版提升。完整方法、计数与边界见 [板端模拟测试](../references/simulation-test-2026-10-26.md)。

这些是实际 S3 解码/LCD 提交结果；本版重新接 iPhone 的画面、触摸目视验收及长时间稳定性仍待确认，不能用模拟发送代替。

## 实测方法

1. BOX USB 接已解锁的 iPhone，允许 CarPlay；无需运行电脑预览。
2. 可选：Mac 连 ATK-CarPlay 诊断热点，双击本项目 `code/tools/collect_performance.command`，按回车采集约 30 秒，在同一个 CarPlay 页面持续滑动。
3. 切回原网络再反馈。脚本保存 `status.jsonl` 与 `summary.json`，帧率由采集区间计数差计算；耗时摘要明确为板端启动以来累计，不能误当采集区间纯解码平均。
4. 优先比较接收/解码/显示 FPS、decode/process/convert/present 耗时、gaps、decoder_resets、skipped_waiting_idr。若仍是每数秒一帧，先判断解码长耗时还是重同步等待，再考虑降低源负载。
