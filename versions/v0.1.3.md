# 0.1.3：低分辨率协商与实际 SPS/PPS 检查

日期：2026-10-26。候选固件 `0.1.3-atk-lowres`。

## 实验目的

0.1.2 板端实测 800×480 High/CABAC 解码约 518–1309 ms，慢解码与队列缺口恢复使高负载只显示约 0.45 FPS。本版先验证手机能否降低实际输出尺寸；不通过 Mac 转码，不把修改声明当作手机已接受，也不预先承诺提高到某个帧率。

## 修改

- `/info` 主屏尺寸由 800×480 改为 **320×192**，保持同样宽高比；maxFPS 仍为 30。物理 LCD 仍为 320×240，画面上下各留 24 像素黑边。
- 两个触摸 contact 的 HID 逻辑上限同步为 320×192；构建时从 plist 生成共享坐标配置，显示触摸映射与 report 边界使用同一值，避免画面变小但坐标仍按 800×480 回传。
- 状态增加 `local_display.requested_width/requested_height/requested_max_fps`，与成功解码后的 `source_width/source_height` 分开。
- 增加只读 `/video-config.h264`，从当前接收队列导出 Annex-B SPS/PPS 配置，不导出视频帧或密钥；没有当前配置时返回 404，禁用 HTTP 缓存。
- 采集工具在性能采集后保存 `stream-config-annex-b.h264` 和 `stream-analysis.json`：实际 Profile、constraint flags、level、编码/裁剪尺寸、参考帧数及 PPS 的熵编码标志。解析失败/404 显式记录，不能冒充 Baseline 或低分辨率成功。
- CPU 240 / PSRAM 80 MHz、解码内核、有界队列与关键帧恢复策略不变。仍支持既有 High/CABAC 样本，手机不降 Profile 时可继续观察。

## Baseline 边界

本轮核对已有接收实现、参考代码和公开项目后，**尚未找到已验证的 CarPlay 强制 Baseline 协商字段**。没有虚构 `profile-level-id`、修改 SPS 标签或把服务器内转码当作手机原生输出。本版只声明低分辨率，并检查实际码流；不能称为已实现 Baseline 强制协商。

Profile 66 且 PPS entropy_coding_mode_flag=0 才有 Baseline/CAVLC 的观察基础；Constrained Baseline 还需检查约束位和其他编码工具。即使观察到这些参数，也不能代替官方解码器接入/正确性和板端速度检查。若仍是 Profile 100 / CABAC=1，则 Baseline 未观察到。

公开参考：

- [esp_h264 支持范围与 S3 基准](https://github.com/espressif/esp-h264-component/blob/master/esp_h264/README.md)：Constrained Baseline；320×192 双任务 27 FPS 是官方基准，不是本项目结果。
- [PlayPort 显示能力声明](https://github.com/youcci/playport)：屏幕尺寸可声明，但不能据此保证 iPhone 接受任意极低尺寸。
- [Apple 模拟器推荐测试尺寸](https://developer.apple.com/documentation/carplay/using-the-carplay-simulator)：不能将 320×192 视为已获支持的真实主屏模式。

## 板端模拟结果（不是 iPhone 协商结果）

同一 S3 固件与 Sub0h264 解码器，通过 USB NCM 接收离线生成的两组 320×192 对照样本。每轮发送 10 秒后另保留会话 3 秒，以前后计数差统计；Profile/参考帧/编码细节有所不同，耗时差不能全部归因于 CABAC。

| 样本 / 目标输入 | 实际发送 / 收到 | 解码 / LCD 提交 | gaps | 解码均值 | 转换均值 | LCD 提交均值 |
|---|---:|---:|---:|---:|---:|---:|
| High/CABAC / 10 FPS | 100 / 100 | 100 / 100 | 0 | 约 46 ms | 约 22 ms | 约 16 ms |
| Baseline/CAVLC / 10 FPS | 100 / 100 | 100 / 100 | 0 | 约 42 ms | 约 22 ms | 约 16 ms |
| High/CABAC / 30 FPS | 300 / 300 | 72 / 72 | 5 | 约 63 ms | 约 24 ms | 约 16 ms |

三轮解码/LCD 错误计数增量均为 0。高负载仍等待 IDR，不能宣称 30 FPS；按含 3 秒收尾的 13.005 秒观测区间计算约 5.54 FPS。两轮 10 FPS 都能完成全部输入，按含收尾的区间计算约 7.69 FPS；持续输入率和包含收尾的平均值应区分。耗时是由舍入后的累计均值与次数差分估算的墙钟时间，扣除了显示回调但包含调度和协作等待。

这些样本由 Mac 离线转码准备，仅用于模拟测试。没有让 Mac 参与独立运行链路，也没有证明 iPhone 会接受小尺寸或 Baseline，更不能当作原始 800×480 码流上仅换 Profile 的同条件加速比。公开数值见 [lowres-simulation-2026-10-26.json](../references/lowres-simulation-2026-10-26.json)。

## 实物验收

1. 核对 BOX 芯片/MAC/分区，完整备份当前 Flash；仅更新当前应用槽，独立读回与保护范围检查。
2. 确认本版实际启动、SPS/PPS 端点空闲返回 404；可用 Mac 模拟器发送原样本，检查端点返回真实 High 配置而非声明尺寸。该步骤不代表 iPhone 接受低分辨率。
3. 断开 BOX 全部供电后，不按 BOOT，直接接已解锁 iPhone，允许 CarPlay（保证此前模拟配置清空）。保持板子接手机供电，Mac 仅连诊断热点，双击 `code/tools/collect_performance.command` 采集性能及 SPS/PPS。
4. 检查实际 width/height、profile_idc、constraints 和 entropy_coding_mode_flag；同时看显示 FPS、gaps、decoder_resets。若拒绝启动、没有 SPS/PPS 或尺寸未变，明确记为未接受/未证实，保留追踪再选择回退或其他尺寸。

声明成功、构建成功和模拟发送成功均不能代替第 3–4 步。

## 真实 iPhone 采集结果

已完成上述手机测试，采集目录 `build/performance/20261026-223120/`（忽略）。30 次采样覆盖 29.07 秒，无采样失败、无计数回退/重启区间。所有采样的解码源尺寸均为 320×192；实际导出的 SPS/PPS 为 **320×192、Profile100 High、CABAC=1、4参考帧、8bit YUV420、逐行、无裁剪**。因此手机接受低分辨率，但本次没有观察到 Baseline 切换。

- 接收 572 帧（19.676 FPS），解码计数增加 156、LCD 提交增加 157（5.401 FPS），错误计数增量 0。采样边界可能包含进行中的解码/提交回调，两个独立计数可相差一帧。
- 采集区间约解码 126.78 ms、转换 24.55 ms、LCD 提交 16.42 ms、总处理 168.31 ms。这些由前后舍入后的累计均值与尝试次数差分估算，属于墙钟时间；不是纯 CPU 或端到端延迟。末次状态里的 112.58 ms 是启动以来解码均值，不能误当本次区间值。
- 期间配置包增加 22 次，队列 epoch 增加 22，IDR 增加 11；gaps 增加 11，解码器重建增加 33。代码核对确认现有队列对每份配置无条件换代并触发重建，即使字节相同。**本轮没有逐份保存配置，尚不能确定其中多少份是完全相同的重复包**；0.1.4 增加严格字节去重及计数来验证。

真实数据说明降低源分辨率这条路径可行，仍未达到稳定流畅目标；现阶段不能换上仅支持 Constrained Baseline 的官方解码器。公开数值与 SPS/PPS 参数见 [iphone-lowres-2026-10-26.json](../references/iphone-lowres-2026-10-26.json)。此次只有计数和码流参数验收，未替用户确认画面观感、颜色和触摸目视结果。
